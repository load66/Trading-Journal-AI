# BonusTracker account questions

`POST /api/bonus-tracker/ask` accepts one question and a bounded list of saved facts. It requires the existing owner authorization check even when the journal middleware is disabled locally. It never queries journal tables, reads uploads, fetches user-supplied URLs, or modifies bonus records. Only the configured Groq connection is used; no fallback sends this context to another provider.

The frontend explains the data sharing before Ask AI is pressed. It sends one bonus's saved terms, lifecycle dates, task counts, canonical closure checks and calculated dates. Notes, account identifiers, other bonuses, transactions and journal data are excluded. Long identifiers are redacted from fact text. Up to 10,000 characters of historical terms are included, with an explicit truncation marker. Current offers and eligibility are not verified by this feature.

AI returns an explanation, supporting fact IDs, and missing information. IDs must exist in the supplied context; newly invented numeric values are rejected. This validates structural grounding, not every semantic claim. Saved facts remain available for review, and existing financial calculations and closure gates remain authoritative. Answers cannot update accounts, execute actions or produce import JSON. Changed facts invalidate client results and cache identity.

Answers begin with the specific question's answer, followed by its saved conditions. The prompt uses canonical next-action and closure-gate facts, preserves combined versus alternative fee waivers and recurring periods, and treats absent fee wording as unknown. Conflicting or shortened evidence calls for verification. The tracker displays its own closure verdict and next step alongside the explanation; AI cannot authorize closure or override those results.

Owner sign-in uses the existing Supabase project and its browser publishable key. Credentials go directly to Supabase Auth. Access and refresh tokens remain in a separate sessionStorage entry, outside tracker backups. Closing the browser clears that session. Refreshes are single-flight; failed authorization clears only the AI session. No auth configuration, tables or policies are changed.

Default allowance is 30 attempts per UTC day per server process, configurable from 1 to 100. Failures count. Calls are serialized with a five-second minimum interval. Each call has a 35-second provider timeout, a 2,000-token output cap and no paid automatic retries. Identical question/context answers can be reused in memory for 15 minutes; the cache has at most 30 entries. Inputs are not persisted; responses are held briefly in the process cache. Counters reset when the process restarts, so this is an app guard rather than a provider billing cap.

Tests use synthetic data. They cover authentication before provider access, fail-closed local configuration, input and answer validation, unknown citations, invented numeric values, cache invalidation, budget handling and sanitized errors. Browser tests cover one-account context, explicit sending, authentication, cited facts, responsive layout, rate limits, disconnect and unchanged saved records. Production provider behavior still depends on the owner's sign-in and available Groq quota.
